## ЦЕЛИ ПРОЕКТА

### 1. Research Prototype

Создать работающий прототип, который демонстрирует:

- Имитацию операционного процесса (обработка заказов).
- AI‑агенты для:
  - прогноза нагрузки,
  - планирования порядка обработки,
  - объяснения рекомендаций.
- Human‑in‑the‑loop интерфейс:
  - оператор видит рекомендации AI,
  - может переопределить решение,
  - система фиксирует override и может учиться на этом.

### 2. Исследовательские вопросы

Ключевые вопросы (не додумывать, а исследовать в прототипе):

1. Как визуализировать решения AI так, чтобы не‑эксперты понимали логику и доверяли системе?
2. Какие типы объяснений (causal, feature importance, «что если») наиболее полезны операторам?
3. Как проектировать human‑in‑the‑loop интерфейсы, где человек может переопределить решение AI?
4. Как измерять влияние AI‑рекомендаций на качество решений (время, дедлайны, удовлетворённость)?

### 3. Подготовка к Фраунгоферу

Подготовить материалы для возможной коллаборации:

- README с исследовательскими вопросами.
- Питч (1 страница, английский) для отправки через Fraunhofer Match или напрямую в институты (IAO, IESE, IOSB, IPA).
- Документацию архитектуры и метрик.

## НАУЧНАЯ РАБОТА (Stage 0, добавлено 31.08.2026)

Проект остаётся **Stage 0 — инструмент для исследования, не проведённое исследование**. Ничего в этом разделе не является результатом — это план. Полная версия с обоснованиями — в `docs/experiment-design.md` (дизайн эксперимента, этика) и `docs/research-paper-outline.md` (структура будущей статьи, без выдуманных цитат).

### Исследовательские вопросы (узкие, измеримые сегодня)

Три, не больше — каждый отвечается на данных, которые прототип уже логирует или экспортирует (`GET /api/decisions/export`):

1. Меняет ли реальное AI-объяснение (в отличие от детерминированного fallback-шаблона) поведение override?
2. Предсказывает ли заявленная уверенность объяснения (`confidence`) принятие vs. override?
3. Занимает ли override больше времени, чем accept?

Четыре более широких вопроса из раздела «Исследовательские вопросы» выше — исходная рамка проекта; три узких выше — то подмножество, которое прототип реально может протестировать сейчас, не замена рамке.

### Гипотезы

- **H1** (по RQ1): нет уверенного направления — override rate может отличаться между `source: "llm"` и `source: "fallback"` в любую сторону. Сформулировано как двусторонний вопрос намеренно.
- **H2** (по RQ2): решения с `confidence: "low"` переопределяются чаще, чем с `"high"`.
- **H3** (по RQ3): медианная `decisionLatencySeconds` выше для `human_overridden`, чем для `human_accepted` — обоснование из самого UI (override требует больше шагов, чем accept), не догадка.

### Метрики: что уже собирается, а что требует нового инструмента

Уже в коде (без изменения схемы БД): `plannedOnTimeRate`, `avgProcessingHours`, `overrideRate`, `avgDecisionLatencySeconds` (`GET /api/metrics`); explanation source/confidence и reason text по каждому решению (`GET /api/decisions/export`).

**Не измеримо без новой работы, честно помечено, не заменено прокси-метрикой:** субъективное доверие оператора к объяснению, когнитивная нагрузка — обоим нужен отдельный опросный инструмент (анкета/шкала), которого в приложении нет. Идентификация конкретного участника/сессии — тоже нет (`decision_log` не хранит participant_id); текущий обходной путь — одна чистая БД на участника, без изменения кода.

### Дизайн эксперимента (предложен, не проведён)

Within-subjects, с балансировкой порядка условий. Условие A — реальное объяснение (`ANTHROPIC_API_KEY` задан); условие B — только fallback (`ANTHROPIC_API_KEY` не задан). Известный пробел: нет UI-переключателя между A/B в рамках одной сессии — только перезапуск сервера с другой переменной окружения. Участники: рекомендация — сначала пилот со студентами/коллегами (реальных операторов из сервисной компании нет данных о доступе), решение о более широком исследовании — после пилота. Полный протокол по шагам — в `docs/experiment-design.md`.

## ПЛАН РАЗРАБОТКИ

### Этап 1 (Stage A): Базовая версия (2–3 недели)

- Генерация синтетических заказов.
- Простой алгоритм планирования (по дедлайну + приоритету).
- Базовый дашборд со списком заказов и планом.
- Бэклог: PT‑01…PT‑08, см. `docs/spec.md`.

### Этап 2 (Stage B): AI‑объяснения (2–3 недели)

- Агент объяснений (LLM), формат — топ‑3 фактора + короткий текст.
- Секция «Explanations» в дашборде.
- Возможность переопределить план и сохранить решение (с указанием причины).

### Этап 3 (Stage C): Метрики и история (2–3 недели)

- История решений (`decision_log`).
- Метрики: % в дедлайн, среднее время, доля override.
- Раздел «Research questions» в README.

### Этап 4 (Stage D): Полировка под демонстрацию (2 недели)

- Демо‑сценарий (3–5 минут показа, ~25 заказов / 5 дней — оценка, требует подтверждения по ходу).
- Улучшение Explanation‑UI (один основной вариант, без альтернатив в MVP).
- Страница/секция «For Researchers» с исследовательскими вопросами и контактами.
